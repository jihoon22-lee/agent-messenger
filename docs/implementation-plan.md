# 구현 계획

이 문서의 M0-M5와 작업 ID는 **문서상의 개발 계획**이다. GitHub Milestone·Issue가 생성되었다는 뜻이 아니다. 현재 구현 단계는 모두 미착수이며 실행 코드·실연동 증거는 없다.

## 1. 단계 개요

| 단계 | 목표 | 선행 조건 | 완료 기준 |
| --- | --- | --- | --- |
| M0 | 사내 계약·보안·네트워크 확인 | 사내 작업 환경 | 실제 API 확인표, 1.18.33 최소 계약, 허용 데이터·작업 범위 |
| M1 | 최소 골격·합성 왕복 | M0의 역할·보안 기준 | Gateway/Runner 분리, 타입·검증, SQLite 장부, 합성 테스트 |
| M2 | 텍스트 요청 → 실제 PC 작업 | M1 + 실제 계약 | 실제 메신저와 실제 사내 모델을 거쳐 로컬 테스트 결과 전달 |
| M3 | 질문·승인·중단이 있는 작업 완주 | M2 | 텍스트 제어, 대기열 우회, stale 처리, 실제 도구 실행 |
| M4 | 개인용 MVP 안정화 | M3 | 복구·보안·중복·긴 답변·오프라인 인수 테스트 통과 |
| M5 | Gateway 운영 VM 이전 | M4 + VM·정책 승인 | PC 실행 유지, Gateway만 이전, 재연결·롤백 검증 |

M1의 합성 작업은 M0의 실제 메신저 자료 확보와 병행 가능하다. 다만 미확인 계약을 추정한 실어댑터를 만들거나 M2 완료로 표시하지 않는다.

## 2. 작은 변경 단위

| 작업 ID | 단계 | 산출물 | 검증·완료 조건 |
| --- | --- | --- | --- |
| P00 | M0 | 사내 확인표·정책·허용 작업 폴더 | 비밀값 없이 확인 여부·차단 요인 기록 |
| P01 | M1 | 저장소 골격·런타임 고정·lockfile·스크립트 | 사내 설치·lint·typecheck·테스트 명령 실제 실행 |
| P02 | M1 | 내부 프로토콜·인증·합성 어댑터 | schema/version/identity/크기 오류 거절, 두 프로세스 왕복 |
| P03 | M1 | inbox·작업 장부·outbox·중복 키 | 트랜잭션·동일 ID 재전달·재시작 테스트 |
| P04 | M2 | OpenCode 1.18.33 어댑터·전용 세션 | 실제 health/auth/요청/완료/세션 지속, 결과 상관관계 |
| P05 | M2 | 사내 메신저 어댑터 | 수신 인증·ACK·발신·자신의 echo 제외, 실제 1:1 왕복 |
| P06 | M3 | 질문·일회 승인·중단·새 대화 | 실제 pending→텍스트 응답→완료, stale·중복·다중 질문 |
| P07 | M3 | 일반 대기열·제어 우선 처리 | 작업 두 개 순서 보장, 승인·중단이 막히지 않음 |
| P08 | M4 | 재연결·복구·불명확한 실행 처리 | SSE/PC/Gateway 재시작, unknown 무재실행, 결과 재전송 |
| P09 | M4 | 답변 분할·속도 제한·로그·진단 | 한글·이모지·코드 블록, 발신 timeout, 민감 로그 미노출 |
| P10 | M4 | 인수 테스트·사내 실행 문서·개인 파일럿 | 사내 실제 모델·메신저 증거와 미검증 항목 보고 |
| P11 | M5 | VM 배포·이전·롤백 | 단일 Gateway 전환, 상태 이전, PC 경로·OpenCode 유지 |

구현 PR은 작업 ID를 참조하는 작은 단위로 분리한다. API 준비 상황에 따라 P04/P05는 병행 가능하다. 커밋·PR·이슈의 실제 생성은 해당 개발 환경에서 별도로 수행한다.

## 3. M0: 보안·계약 확인

메신저 관리 부서의 실제 수신·발신 계약은 사내에서만 확인한다. 서명 검증, ACK와 재전송, 이벤트 ID, 봇 echo, 허용 수신 주소, 메시지 길이·빈도, 발신 조회·멱등 키를 기록한다.

OpenCode는 버전·help·health·명세부터 확인하고, 격리한 테스트 폴더와 메신저 전용 세션으로 요청·질문·권한·중단을 검증할 계획을 만든다. 기존 글로벌 설정을 임의 교체하지 않는다. 앱카드 도입이나 메신저용 MCP로 문제를 우회하지 않는다.

**통과 조건:** 환경 제약과 미확인 항목이 분리되고, 사용할 런타임·사내 모델·테스트 폴더·데이터 보관 위치가 정해진다. 세부 API가 막힌 항목은 M0 미완료로 남기되 독립적인 합성 개발은 계속할 수 있다.

## 4. M1: 최소 골격

Gateway와 Runner를 같은 PC에서 실행하되 네트워크 계약으로만 연결한다. 먼저 합성 메신저 어댑터와 가짜 OpenCode 서버로 전체 경로를 테스트한다. DB migration·단일 Runner 잠금·안전한 로그·프로토콜 버전·크기 제한을 작게 구현한다.

인증·중복 처리를 나중에 붙이기 위해 실수신 엔드포인트를 무인증으로 열지 않는다. queue와 outbox를 메모리 배열만으로 만들고 운영 복구가 된다고 주장하지 않는다.

**통과 조건:** 합성 입력 하나가 한 번만 기록·전달되고 결과 한 개가 outbox를 거쳐 반환된다. Gateway/Runner를 독립 재시작해 저장 상태를 읽을 수 있다. 이 결과는 실제 사내 연동 성공이 아니다.

## 5. M2: 실제 왕복

P04는 OpenCode 전용 세션 생성·재사용과 실제 결과 수집을 구현한다. P05는 업체 계약에 맞춘 수신·발신만 책임진다. 실제 메신저에 민감하지 않은 요청을 보내고, 실제 사내 모델이 로컬 테스트 파일을 읽어 얻은 결과를 받는다.

**통과 조건:** 같은 대화의 후속 질문이 이어지고, 사용자·대화방·세션·실제 파일 결과가 정확하다. 본인의 다른 CLI/브라우저 세션을 읽거나 변경하지 않는다. 작업 중 질문·승인이 필요하면 미지원 상태를 명시하고 안전하게 종료한다. M3 전에는 일반 업무용으로 열지 않는다.

## 6. M3: 대화형 작업 완주

실제 OpenCode가 생성한 질문·권한 요청을 사용한다. 모델이 자연어로 “승인해주세요”라고 적은 것만으로 권한 이벤트를 대체하지 않는다. 일회 승인·거절, 선택·자유 입력·복수 질문, 중단·상태·새 대화와 충돌 방지를 구현한다.

**통과 조건:** 실제 pending 상태가 텍스트 응답으로 해소되고 작업이 완료된다. 동일·만료·다른 대화의 승인은 실행을 유발하지 않는다. 작업 B가 대기 중이어도 작업 A의 승인은 즉시 전달된다. 중단 후 부작용이 자동 복구됐다고 안내하지 않는다.

## 7. M4: 개인용 MVP

연결 유실·프로세스 종료를 실행 경계마다 주입한다. 업스트림 반영 여부가 불분명한 작업은 보류하고 재실행하지 않는다. 발신 실패와 실행 실패를 분리하며 결과만 재전달한다. Gateway 오프라인 동안 완료한 PC 결과도 outbox로 복구한다.

긴 답변·정확한 단위의 제한·rate limit·로그 마스킹·테스트 증거를 보완한다. 메신저가 발신 조회를 제공하지 않는 경우의 중복 위험과 처리 정책을 운영 문서에 남긴다.

**통과 조건:** [테스트](testing.md)의 MVP 필수 항목 통과, 사내 실연동 필수 증거 확보, 미검증·제약 공개. 개인 파일럿에서도 본인 1:1과 허용 작업 범위는 유지한다.

## 8. M5: VM 이전

Gateway를 옮기며 OpenCode를 재설치하거나 PC 작업 경로를 바꾸지 않는다. 일시 수신 정지·기존 작업 drain·DB 일관 백업·웹훅 전환·Runner 주소·TLS·인증 변경을 [운영 문서](operations.md)에 따라 진행한다.

**통과 조건:** 운영 VM으로 들어온 메시지가 본인 PC에서 실행된다. PC가 꺼지면 실행 불가를 안내한다. 이전·롤백 중 Gateway 두 개가 동시에 요청을 실행하지 않는다. 이전 후 받은 메시지는 오래된 백업으로 조용히 유실시키지 않는다.

## 9. 후속 확장

MVP와 분리해서 검토할 후보는 agent-browser 도구 연결, 범용 승인·선택 앱카드, 사전 등록 프로젝트 선택, 파일 첨부, 제한된 장기 기억·예약 작업이다. 각 기능은 별도 위협 모델과 인수 기준이 필요하다. 지금 이 후보의 코드·의존성·UI를 미리 만들지 않는다.

## 10. 작업 상태 기록 규칙

완료 표시는 증거와 함께만 바꾼다. 예: `P04 구현 완료 / 합성 PASS / 1.18.33 API PASS / 실제 모델 미검증`. 날짜와 코드 commit, 비식별 테스트 결과, 남은 차단 요인을 기록한다. 문서상의 체크리스트와 GitHub Milestone의 상태를 혼동하지 않는다.
