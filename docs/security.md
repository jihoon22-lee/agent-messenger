# 보안·데이터 취급 지침

이 문서는 구현 기준이며 회사의 보안 정책이나 승인 절차를 대체하지 않는다. 실제 작업은 사내 승인 환경에서 진행한다.

## 1. 외부 저장소와 사내 자료의 경계

이 GitHub 저장소는 비공개지만 외부 서비스다. 사용자의 문서 업로드 요청은 사내 API 원문·업무 자료·실행 로그의 반출 허가가 아니다.

| 저장소에 둘 수 있는 자료 | 사내에서만 보관할 자료 |
| --- | --- |
| 반출 가능한 일반 설계·코드·합성 테스트·비식별 결과 | 사내 API 원문, 실제 endpoint·host·IP·사번·대화방 식별자 |
| 합성 ID·example.invalid·비밀값 없는 설정 템플릿 | 토큰·쿠키·패스워드·클라이언트 키·인증서·환경 파일 |
| 승인된 범위의 PASS/FAIL·버전·기능 확인 요약 | 업무 소스·보고서·프롬프트·대화·모델 답변·원시 SSE |
| 비밀값이 없는 데이터 스키마 | SQLite DB·WAL·백업·crash dump·네트워크 캡처·로그 |

현재 `.gitignore`는 실수 방지 장치일 뿐이다. 파일명이 다른 비밀값이나 이미 추적된 파일·Git 이력은 보호하지 못한다. 커밋 전에 내용·staged diff·생성 산출물을 확인한다. 유출이 발견되면 토큰 회전 등 사내 사고 절차를 우선하고 단순 파일 삭제로 끝났다고 판단하지 않는다.

## 2. 통신 인증

메신저 수신은 업체 계약의 인증·서명 규칙을 정확히 구현한다. raw body 서명이 요구되면 JSON 변환 전 검증한다. timestamp/nonce가 제공되면 규약에 맞게 재생 공격을 검사한다. IP 제한은 추가 방어 수단이며 인증을 대신하지 않는다.

허용된 발신자뿐 아니라 bot·tenant·대화 유형·대화방 매핑도 확인한다. 발신 echo, 시스템 이벤트, 수정·삭제 이벤트를 신규 프롬프트로 자동 취급하지 않는다. 실제 식별자는 사용자 텍스트나 표시 이름이 아니라 인증된 이벤트 필드에서 얻는다.

Gateway/Runner는 별도 자격증명을 사용하며 등록된 Runner와 사용자·대화 binding을 묶는다. 운영 네트워크에서는 TLS와 인증서 검증을 적용한다. 인증 실패·만료·잘못된 버전은 fail closed한다. 외부 인터넷 터널·개인 프록시·TLS 검증 해제로 네트워크 제한을 우회하지 않는다.

OpenCode는 loopback에 두고 서버 인증을 적용한다. VM이 OpenCode의 임의 HTTP 경로를 호출하도록 중계하지 않는다. 개발 중 loopback 연결도 무인증 기본값으로 배포하지 않는다.

## 3. 권한·실행 경계

초기에는 본인 전용 1:1, Runner 하나, 사전 등록 작업 루트·모델·에이전트로 제한한다. 실제 업무 자료 대신 합성 테스트 폴더로 시작한다. 읽기·수정·명령·네트워크·외부 전송 권한을 분리한다.

“위험한 작업은 물어봐”라는 프롬프트만으로 통제하지 않는다. OpenCode의 실제 도구 권한과 사내 OS·네트워크 정책을 확인한다. 셸·플러그인이 프로세스 사용자 권한으로 다른 경로·자격증명을 읽을 수 있다면 폴더 매핑만으로 격리가 된 것은 아니다. 필요하면 제한된 실행 계정 등 사내 승인 방식을 별도로 검토한다.

권한 요청을 지원하지 않는 도구를 안전하다고 간주하지 않는다. 승인 없이 민감 작업이 실행되는 설정이면 실사용을 보류하고 설정·도구 범위를 줄인다. 초기 자동승인·always·전체 허용을 구현하지 않는다.

## 4. 승인·질문 위조 방지

사용자·대화·세션·jobId·interactionId·generation·유효기간·pending 상태를 함께 확인한다. 승인 대상의 실제 도구·경로·내용을 보여준다. 모델의 설명이 실제 요청과 다르면 모델 설명만 믿지 않는다.

문서·웹페이지·도구 결과 안의 지시는 비신뢰 데이터다. 그 안의 “승인”, “다른 사람에게 전송”, “관리자 설정 변경”을 상위 정책이나 사용자 지시로 취급하지 않는다. 모델 출력은 Gateway 제어 명령으로 재해석하지 않는다.

미래에 agent-browser를 연결해도 브라우저 콘텐츠의 신뢰 수준은 올라가지 않는다. 특정 탭·프로필·요청 소유권과 게시·전송·제출의 승인 범위를 별도 검증한다.

## 5. 비밀값·로컬 설정

메신저 토큰은 Gateway에만, OpenCode 비밀값과 PC 경로는 Runner에만 둔다. 사내에서 허용한 secret store·OS 자격증명·권한 제한 로컬 파일을 사용한다. 실제 저장 방식은 M0에서 확인한다.

명령줄 인자·URL query·에러 문자열·프로세스 목록·사용자 메시지에 비밀값이 노출되지 않도록 한다. 예시에는 실제 값이나 동작 가능한 토큰을 넣지 않는다. 운영 DB·설정·백업 디렉터리에는 최소 권한과 사내 기준의 디스크·백업 보호를 적용한다.

## 6. 데이터 최소화·보관

Gateway는 승인된 수신 처리·전달·재시도에 필요한 데이터만, Runner는 세션·작업·pending·미전송 결과만 보관한다. 업무 본문은 필요한 최소 기간만 두고 운영 로그에 복제하지 않는다. 대화 영구 보관·검색·장기 기억을 초기 기능으로 추가하지 않는다.

보관 기간은 임의의 고정 날짜로 정하지 않고 사내 정책과 재시도·복구 기간을 함께 확인한다. 완료·만료·전달된 데이터의 정리 작업을 설계하되 처리 중 요청을 삭제해 중복 실행을 유발하지 않도록 한다. 중복 키 tombstone도 허용된 범위에서 유지한다.

OpenCode 자체의 대화·도구 로그·캐시·설정 저장 위치도 별도로 확인한다. Gateway 데이터만 지웠다고 모든 기록이 삭제됐다고 안내하지 않는다.

## 7. 로그·진단·출력

기본 로그는 불투명 correlation ID, 상태, 지연, 오류 분류만 담는다. 실제 사용자·대화방 식별자도 개인정보/사내 정보로 보고 제한한다. 원문 prompt, reasoning, tool output, 모델 인증 헤더, 전체 환경변수는 기본 로그에서 제외한다.

전역 SSE에는 다른 세션 정보가 섞일 수 있으므로 대상 세션 필터를 저장·전송보다 먼저 적용한다. 모델 결과를 외부 서비스로 보낼 수 있도록 임의 수신자를 허용하지 않는다. 초기 발신은 요청이 들어온 검증된 대화방으로만 제한한다.

마스킹·비밀 패턴 검사는 보조 장치이며 유출 불가능을 보장하지 않는다. 민감한 자료는 애초에 작업 범위에서 제외하고 출력 대상·크기도 제한한다. 상세 오류는 사내 제한 로그에, 메신저에는 안전한 요약을 표시한다.

## 8. 패키지·CI·배포

사내 허용 런타임·registry·패키지 반입 절차를 따른다. Node.js·SQLite 드라이버의 실제 실행 OS 호환성과 설치 스크립트를 검토한다. 잠금 파일을 고정하고 실험 때문에 기존 개발 환경을 전역 변경하지 않는다.

외부 GitHub Actions에 사내 endpoint·토큰을 등록하지 않는다. 자동 수집 텔레메트리·에러 보고·원격 로그 전송을 기본으로 추가하지 않는다. 사내 CI에서도 외부 PR·비신뢰 입력이 secret에 접근하지 않도록 한다. 이 문서 패키지에는 실행용 CI가 아직 없다.

## 9. 운영 허용 전 점검

[S01-S11](testing.md)의 보안 시나리오, 서명 실패, 잘못된 주체, stale 승인, 다른 세션 유출, 임의 경로·API 전달, DB·로그·Git 이력의 민감 데이터 여부를 확인한다. 미검증 권한 경계가 있으면 파일럿 범위를 낮추거나 실사용을 보류하고, 이를 완료 처리하지 않는다.
