# 개발 배치·운영·VM 이전

아직 제품 실행 스크립트나 서비스 설정은 구현되지 않았다. 아래는 **운영 설계와 확인 절차**다. 실제 명령은 해당 단계에서 구현·검증한 뒤 추가한다.

## 1. 초기 PC 배치

Gateway와 Runner를 사내 PC에 둔다. Runner는 OpenCode와 같은 실행 환경을 우선 사용한다. WSL 실행이면 같은 WSL 내부에서, Windows 네이티브면 Windows에서 localhost API를 사용한다.

Gateway의 메신저 수신 주소는 관리 부서가 PC에 접근할 수 있는 승인된 경로여야 한다. WSL loopback이나 동적으로 바뀌는 내부 주소를 수신 URL로 바로 등록할 수 있다고 가정하지 않는다. DNS·TLS·프록시·방화벽·수신 포트와 callback 등록 절차를 사내에서 확인한다.

초기에는 사용자가 준비한 OpenCode `serve`에 연결한다. 기동 helper를 만들더라도 소유한 프로세스만 종료하고, 기존 CLI·브라우저 작업용 서버를 임의 종료하지 않는다. 자동 Windows/WSL 탐지·GUI 설치기는 초기 필수 기능이 아니다.

## 2. 설정 경계

다음은 논리 설정 목록이다. 실제 환경변수 이름이나 제품 설정 스키마는 아직 확정하지 않았다.

| Gateway 전용 | Runner 전용 |
| --- | --- |
| 수신 bind/TLS·웹훅 인증 | Gateway 주소·Runner 자격증명 |
| 발신 API·비밀값 참조 | OpenCode localhost 주소·비밀값 참조 |
| 허용 사용자·1:1 대화·bot 매핑 | 허용 workspace binding·작업 디렉터리 |
| Runner 등록·인증 | 고정 agent·사내 provider/model |
| Gateway DB·로그·보관·발신 한도 | Runner DB·로그·단일 인스턴스 잠금 |
| 전달 대기열·오프라인 유효기간 | 실행·질문·승인·중단 timeout 정책 |

실제 설정·DB·로그·사내 증거는 repository 밖의 승인된 저장 경로에 둔다. Gateway와 Runner가 같은 PC에 있어도 별도 상태 파일을 사용한다. `/mnt/c`와 WSL 파일 시스템 중 어디에 저장할지는 해당 런타임·SQLite 드라이버로 검증한다.

## 3. 기동·종료 원칙

기동 시 설정·비밀값 참조·DB migration·디스크 권한을 확인한다. Runner는 단일 인스턴스 잠금을 얻고 OpenCode 버전·접근·등록 세션 상태를 조정한 뒤 실행 가능 상태를 알린다. Gateway는 인증·DB 준비가 안 되면 수신 완료를 거짓 ACK하지 않는다.

일반 요청을 받는 준비 상태와 PC가 실제 실행 가능한 상태는 다르다. Gateway health만 정상이라고 에이전트 전체가 정상이라고 표시하지 않는다.

종료할 때 신규 작업 배정을 중지하고, 진행 중 작업·pending·outbox를 기록한다. 가능하면 안전하게 drain하고, 강제 종료가 필요하면 재기동에서 unknown 상태를 조정한다. 프로세스 종료가 도구 실행 취소나 파일 롤백을 보장하지 않는다.

## 4. PC 오프라인 정책

Gateway가 VM에 있어도 PC가 꺼져 있거나 Runner/OpenCode가 끊어지면 실제 작업은 실행할 수 없다. 다음과 같이 안내한다.

```text
PC가 연결되어 있지 않아 요청을 보류했습니다.
연결 후 '재개 J12'로 시작할 수 있습니다.
```

보류에는 용량·개수·유효기간 제한을 둔다. 재연결 시 자동 실행하지 않는 것을 초기 기본값으로 한다. 이미 접수된 실행의 결과가 불명확한 경우는 오프라인 미실행 요청과 구분하고, `재개`로 다시 실행하지 않는다.

Runner가 작업 중 Gateway와 끊어지면 PC 작업이 계속될 수 있다. 완료 결과는 Runner outbox에 두고 재연결 후 전달한다. 확인되지 않은 상태를 성공·실패로 단정하지 않는다.

## 5. 상태 확인·진단

진단은 Gateway 수신·DB·발신 상태, Runner 연결, OpenCode health/version, 현재 작업·pending·outbox를 나누어 보여준다. 기본 진단에는 모델 키·endpoint·사내 경로·원시 대화가 없어야 한다.

| 증상 | 우선 확인 | 하지 않을 일 |
| --- | --- | --- |
| 수신 자체가 없음 | callback·TLS·서명·방화벽·업체 재시도 | 외부 터널로 우회 |
| 접수 후 실행 안 됨 | Runner/OpenCode 상태·보류·대기열 | 동일 요청 무조건 재제출 |
| 승인 후 정지 | pending ID·만료·세션·API 결과 | 전체 자동승인 활성화 |
| 답변만 안 옴 | Runner/Gateway outbox·발신 상태 | 완료된 PC 작업 재실행 |
| 재연결 후 상태 불명 | 실제 세션·메시지·pending 조정 | idle만으로 성공 또는 미실행 판정 |

## 6. VM 이전 사전 조건

M4 개인용 MVP가 검증되고 VM·DNS·TLS·포트·패키지·서비스 계정·보관 정책이 승인되어야 한다. VM은 메신저 수신과 발신 API 접근이 가능해야 하고, PC에서 VM으로 인증 연결이 가능해야 한다. WebSocket이 허용되지 않으면 전송 어댑터 대안을 별도로 구현·테스트한다.

이전 대상은 Gateway 실행물·설정·비밀값의 승인된 이전/재발급·Gateway DB다. OpenCode 설치, PC 작업 파일, 전용 세션, Runner DB, PC 인증정보는 옮기지 않는다.

## 7. VM 이전 순서

1. **전환 준비:** 기존 요청·outbox·중복 키와 백업 시점을 기록하고 callback 전환·복구 방법을 확인한다.
2. **신규 배정 정지:** 가능하면 수신을 승인된 방식으로 일시 보류하고 실행을 drain한다. 수신이 계속되면 그 입력까지 일관되게 인계할 절차를 정한다.
3. **일관 백업:** Gateway를 정지한 상태로 SQLite 본체·관련 상태를 일관되게 복사하거나 검증된 SQLite 백업 기능을 사용한다. 쓰는 중인 DB 본체만 복사하지 않는다.
4. **VM 준비:** 동일 버전·schema의 Gateway와 승인된 설정·비밀값을 준비한다. 신규 수신·발신 소비는 아직 시작하지 않는다.
5. **연결 전환:** Runner의 Gateway 주소·TLS 신뢰·인증을 바꾸고 복구 상태를 확인한다. 동시에 두 Gateway가 실행 요청을 배정하지 않도록 한다.
6. **callback 전환:** 업체 절차로 수신 주소를 VM으로 변경한다. 기존 PC Gateway의 소비·발신은 비활성화한다.
7. **상태 조정:** 재전송 webhook, 미전달 결과, 미완료 outbox를 기존 키로 조정한다. 오래된 보류 작업은 자동 실행하지 않는다.
8. **검증:** 실제 메신저→VM→PC→메신저 왕복, 승인·중단·offline, D01-D04를 확인한다.

수신 URL만 바꾸면 완전 이전된다고 가정하지 않는다. 인증·DB·메신저 등록·네트워크·미처리 상태까지 함께 전환해야 한다.

## 8. 롤백

새 Gateway의 신규 수신·배정을 먼저 멈춘다. 이전 후 새로 받은 입력, 완료 작업, 발신 결과, 중복 키를 기존 환경으로 안전하게 인계하거나 별도 보류한다. 오래된 DB 백업만 복원해 이후 입력을 잃거나 완료 작업을 다시 실행하지 않는다.

callback과 Runner 연결을 승인된 이전 주소로 되돌리고, 단일 Gateway만 소비하도록 한다. schema 변경이 있다면 호환 버전·역마이그레이션 가능 여부를 먼저 확인한다. 롤백 후 실제 왕복과 pending/outbox를 재검증한다.

## 9. 업데이트·보관·복구

Gateway와 Runner의 프로토콜 버전 호환을 확인하고, 불일치 시 작업을 안전하게 보류한다. PC의 OpenCode를 함께 자동 업그레이드하지 않는다. 백업·복원 시험에는 복원 직후 신규 실행을 막는 절차를 포함한다. 오래된 실행 장부로 인해 동일 업무가 반복될 수 있기 때문이다.

복구 판단이 끝나기 전 DB를 지우거나 세션을 초기화하지 않는다. 실제 복구 명령과 서비스 등록 방식은 M4/M5에서 사내 환경에 맞게 작성한다.
