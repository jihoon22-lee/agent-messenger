# 요구사항과 범위

기준일: 2026-10-15. `U`는 사용자 확정 요구, `B`는 권장 구현 기준, `V`는 사내 확인 항목이다. 구현 기준을 바꿀 때는 [결정 기록](decisions.md)을 갱신한다.

## 1. 사용자 확정 요구

| ID | 요구사항 | 구현에 미치는 영향 |
| --- | --- | --- |
| U01 | 실제 업무는 본인의 사내 PC OpenCode가 수행한다. | 원격 VM 실행이나 외부 작업 환경으로 대체하지 않는다. |
| U02 | 사내 설치본은 OpenCode 1.18.33이다. | 설치본 API·이벤트를 기준으로 검증한다. |
| U03 | 개발 중에는 수신 서버도 PC에 둔다. | VM 발급을 개발 선행 조건으로 만들지 않는다. |
| U04 | 안정화 후 수신 서버를 운영 VM으로 이전한다. | PC 연결 계층과 메신저 연결 계층을 분리한다. |
| U05 | 메신저용 MCP는 초기 구조에 필요하지 않다. | Bridge 자체를 MCP로 구현하지 않는다. |
| U06 | 먼저 agent-messenger를 빠르게 검증·개발한다. | agent-browser 연결은 초기 완료 조건이 아니다. |
| U07 | 최종적으로 agent-browser 연결을 고려한다. | OpenCode 도구 확장은 가능하게 두되 현재 브라우저 코드를 포함하지 않는다. |
| U08 | CLI·브라우저 패널과 메신저 대화를 이어갈 필요가 없다. | 메신저 전용 세션, 세션 선택 UI 불필요. |
| U09 | 개인 비서처럼 대화하는 챗봇 경험을 원한다. | 일상적 대화는 자연스럽게, 세션 ID·내부 상태는 필요할 때만 표시한다. |
| U10 | 초기에는 앱카드를 제외한다. | 질문·승인을 텍스트로 처리한다. |
| U11 | 안정화 후 승인·선택 질문에 앱카드를 검토할 수 있다. | 카드 도입은 표현 계층의 후속 확장이다. |
| U12 | 실제 개발은 보안상 사내에서 한다. | 외부에는 반출 가능한 비식별 문서·예제만 남긴다. |
| U13 | 기존 사내 OpenCode·사내 LLM 환경을 이용한다. | Gateway/Runner에 외부 모델이나 별도 LLM 호출을 추가하지 않는다. |

메신저 관리 부서는 발신 API를 제공하며, 수신은 별도 수신 서버 또는 앱카드 기반 방식이 필요하다는 것이 사용자가 제공한 전제다. 구체적인 API·인증·네트워크 규칙은 아직 확인하지 않았다.

## 2. 권장 초기 구현 기준

| ID | 기준 | 이유·변경 범위 |
| --- | --- | --- |
| B01 | 본인 전용, 1:1 대화, 등록된 Runner 하나 | 권한·라우팅 복잡도를 줄인다. 다중 사용자 확장은 별도 설계가 필요하다. |
| B02 | 한 실행 환경에서 한 번에 한 일반 작업 | 실행 충돌 방지. 제어 메시지는 대기열을 우회한다. |
| B03 | 단일 저장소, Gateway와 Runner 두 실행 모드 | 초기 동시 실행과 이후 Gateway VM 이전을 양립한다. |
| B04 | TypeScript + Node.js + SQLite | 통신 코드 재사용과 작은 운영 규모를 위한 제안. 사내 런타임·패키지 정책 우선. |
| B05 | Runner가 Gateway로 outbound WebSocket 연결 | PC OpenCode 포트를 외부에 공개하지 않기 위함. 차단되면 HTTPS long polling을 별도 검토한다. |
| B06 | 한 대화방의 전용 세션을 지속 사용 | 대화 연속성 제공. 영구 기억을 보장하지 않는다. |
| B07 | 처음에는 명시적으로 준비된 OpenCode serve에 연결 | 자동 설치·프로세스 관리자·Windows/WSL 탐지를 선행 개발하지 않는다. |
| B08 | 하나의 사전 등록 작업 디렉터리·모델·에이전트 | 프로젝트 선택·모델 선택 UI를 제외한다. 접근 범위는 운영자가 로컬 설정한다. |
| B09 | 일회 승인만 허용하고 모호한 입력은 거절 | 초기 무인 위험을 낮춘다. 권한 범위는 실제 도구 설정에서 강제한다. |
| B10 | 오프라인 보류 작업은 재연결 후 명시적 재개 | 오래된 요청이 예기치 않게 실행되는 것을 방지한다. |

## 3. MVP 사용자 기능

| 기능 | 반드시 되는 동작 |
| --- | --- |
| 일반 대화 | 메신저 텍스트를 전용 세션에 전달하고 실제 응답을 같은 대화방으로 보낸다. |
| 대화 지속 | 다음 메시지가 앞선 대화의 맥락을 이어간다. 재시작 후에도 매핑을 복구한다. |
| 실제 작업 | 지정된 로컬 테스트 파일 읽기, 승인된 제한 작업을 실제 PC에서 실행한다. |
| 질문 | 단일 선택·자유 입력을 처리하고, 복수 질문도 누락 없이 안내한다. |
| 권한 | 요청 내용과 대상을 설명하고, ID를 붙인 일회 승인·거절을 처리한다. |
| 상태·중단 | 상태를 모델 호출 없이 확인하고, 실행 중단 요청과 실제 중단 확인을 구분한다. |
| 새 대화 | 기존 작업과 충돌하지 않게 새 세션을 연결한다. 기존 기록을 몰래 삭제하지 않는다. |
| 결과 전달 | 접수·필요한 진행·최종 결과만 전송한다. 긴 텍스트를 안전하게 분할한다. |
| 장애 대응 | 중복 수신, 전송 실패, PC 오프라인, SSE 단절, 재시작을 구분해 처리한다. |

## 4. 초기 범위에서 제외

메신저 MCP, 앱카드, 브라우저 원격 제어, Chrome 설치기, CLI 세션 동기화, 전체 OpenCode 관리 UI, 다중 사용자·단체방, 사용자 임의 실행 PC·작업 경로 지정, 파일 업로드·다운로드, 메시지 편집 UX, 예약 작업·선제 알림, 복잡한 장기 기억·검색 DB, 범용 ACP/여러 하네스 지원은 제외한다.

제외는 영구 금지가 아니라 이번 MVP의 선행 조건으로 만들지 않는다는 뜻이다. 추후 기능은 우선순위와 보안 검토를 거쳐 별도 작업으로 등록한다.

## 5. 아직 사내에서 확인할 것

| ID | 확인 내용 | 확인 전의 처리 |
| --- | --- | --- |
| V01 | 메신저 수신 방식, 요청 서명·인증, 본문 형태, ACK 형식·제한 시간 | 실제 HTTP 계약은 만들지 않고 합성 어댑터로 격리한다. |
| V02 | 안정적인 이벤트·메시지 ID, 재전송·순서·수정·삭제 이벤트, 봇 발신 echo | 본문 해시만으로 중복 제거하거나 모든 이벤트를 사용자 입력으로 취급하지 않는다. |
| V03 | 발신 인증, 동일 대화방 답장, 크기·빈도 제한, idempotency·전송 조회 지원 | 정확한 발신 보장·제한 수치를 추정하지 않는다. |
| V04 | PC/WSL 수신 경로, 포트·DNS·TLS·프록시·방화벽 허용 범위 | 무단 우회하지 않는다. |
| V05 | 1.18.33 실제 API·인증·질문·권한·완료·중단·설정 격리 | 참고 버전과 구분하고 실제 테스트로 계약을 고정한다. |
| V06 | 허용 작업 폴더·도구·모델, 보관 기간, 진단 데이터 위치 | 가장 작은 테스트 범위로 시작하고 민감 데이터는 저장하지 않는다. |
| V07 | Node.js·패키지·SQLite 드라이버 반입 및 Windows/WSL 지원 | 사내 사용 가능한 조합을 선정한다. |

PC 실행, OpenCode 버전, 개발 장소, 초기 앱카드 제외는 미정 사항이 아니다. 이를 다시 선택하도록 요구하지 않는다.

## 6. 성공 판단

기능이 “설계됨”, “구현됨”, “합성 테스트 통과”, “실제 API 통과”, “실제 모델·메신저 통과” 중 어디까지인지 구분한다. 첫 개인 파일럿은 [M4 완료 조건](implementation-plan.md)과 [실연동 인수 테스트](testing.md)를 통과한 뒤 시작한다.
