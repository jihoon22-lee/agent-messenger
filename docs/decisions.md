# 결정 기록

기준일: 2026-10-15. **확정 요구**는 사용자의 명시적 선택이며, **권장 기준**은 이 문서 패키지의 초기 구현안이다. 미검증 기술 사실을 결정으로 확정하지 않는다.

## D01. MCP가 아니라 메신저 클라이언트 — 확정 요구

메신저 입력을 OpenCode 세션에 넣고 결과를 돌려주는 것은 클라이언트·실행 제어 역할이다. 메신저용 MCP를 초기 구현하지 않는다. 기본 응답 전송을 모델의 도구 호출 판단에 맡기지 않는다.

후속으로 에이전트가 명시적으로 다른 대화방에 발신하는 도구를 제공할 때만 별도 MCP 필요성을 검토한다. 초기 발신은 원래 대화방으로 제한한다.

## D02. 실행은 사내 PC에 유지 — 확정 요구

본인 파일·개발 도구·인증 환경을 이용해야 하므로 OpenCode는 PC에 남는다. 수신 서버 VM 이전을 실행 환경 이전으로 해석하지 않는다.

## D03. Gateway/Runner 분리 — 권장 기준

개발 중 모두 PC에 두고 이후 Gateway만 옮기기 위한 역할 분리다. 처음부터 서로 다른 저장소·마이크로서비스 인프라를 만드는 것이 아니다. 단일 저장소·두 실행 모드로 시작한다.

## D04. PC 발신 연결 — 권장 기준

Runner가 Gateway로 연결하는 WebSocket을 우선 검토한다. OpenCode 포트를 외부에 공개하거나 VM이 PC에 임의 HTTP 요청을 보내는 프록시를 피한다. 네트워크가 허용하지 않으면 인증된 HTTPS long polling을 전송 어댑터 수준에서 검토한다. 두 방식을 처음부터 모두 구현하지 않는다.

## D05. TypeScript/Node.js/SQLite — 권장 기준

기존 HTTP/SSE 코드 재사용과 소규모 단일 사용자 운영을 위한 제안이다. 사내 사용 가능 버전·패키지·OS 검증이 우선이다. Redis/Kafka·벡터 DB·별도 웹 UI를 초기 필수 구성으로 추가하지 않는다.

## D06. 메신저 전용 세션 — 확정 요구에 따른 구현 기준

CLI·브라우저 패널과 대화를 공유할 필요가 없다. 메신저 안에서는 전용 세션을 유지해 연속 대화를 제공한다. 세션 선택 UI와 기존 CLI 대화 가져오기는 제외한다. 전용 세션은 영구 장기 기억이나 보안 샌드박스가 아니다.

## D07. 텍스트 우선 — 확정 요구

초기 앱카드를 제외한다. 질문·승인은 텍스트로 구현하고, 안정화 뒤 범용 카드 표현을 선택적으로 추가할 수 있다. 카드 없음이 승인 기능 없음으로 이어지면 안 된다.

## D08. 본인 1:1·한 작업 — 권장 기준

첫 파일럿을 작게 유지한다. 일반 요청은 직렬화하지만 승인·질문·중단은 우선 처리한다. 다중 사용자나 단체방을 추가하려면 실행 계정·파일·자격증명 격리부터 다시 설계한다.

## D09. 중복 억제와 불명확한 상태 보류 — 권장 안전 기준

inbox/outbox·안정적인 jobId·실행 장부로 재전달을 처리한다. upstream 멱등성이 확인되지 않은 작업의 exactly-once를 약속하지 않는다. 실행 반영 여부가 불명확하면 재실행보다 보류를 택한다. 결과 발신 실패는 PC 작업 재실행 사유가 아니다.

## D10. agent-browser는 후속 — 확정 요구

메신저 단독으로 실제 작업을 완료한 뒤 기존 브라우저 도구를 연결한다. 공통 코드 추출은 필요한 최소 범위로 하며 agent-browser 리팩토링·설치기·iframe/DOM 문제 해결을 선행 과제로 끌어오지 않는다.

## D11. 사내 개발·외부 비식별 문서 — 확정 요구와 보안 기준

실제 구현·API·모델·메신저 검증은 사내에서 수행한다. 이 저장소에는 승인된 일반 코드·합성 예제·비식별 문서만 보관한다. private 저장소라는 이유로 사내 원문 데이터를 반출하지 않는다.

## D12. 대상 버전 실측 우선 — 권장 검증 기준

대상은 사용자 확인 OpenCode 1.18.33이다. 1.18.29 참고 문서·공개 최신 문서를 무검증으로 그대로 적용하지 않는다. 실측 API·설정·모델 동작을 분리해 증거를 남긴다. 설치본 업그레이드는 이 프로젝트의 선행 요구가 아니다.

## 변경 절차

권장 기준 변경은 이유, 대안, 보안·운영 영향, 마이그레이션·테스트를 기록한다. 사용자 확정 요구 변경은 명시적인 새 요구를 근거로 한다. 빠른 구현을 이유로 인증·승인·불명확한 재실행 보류를 조용히 제거하지 않는다.
