# 사내 개발 인수인계

## 1. 현재 전달 상태

이 저장소는 요구사항·설계·구현 순서·검증 계획을 전달하는 문서 패키지다. 실제 Gateway/Runner 코드, 사내 메신저 어댑터, 테스트 스크립트, 실행용 CI는 아직 없다. 아래 항목은 앞으로 사내에서 수행한다.

이미 결정한 내용은 다시 질문하지 않는다: OpenCode는 본인의 사내 PC, 설치 버전 1.18.33, 개발 중 수신 서버도 PC, 안정화 후 Gateway만 VM 이전, 초기 MCP·앱카드·브라우저 연계·CLI 세션 공유 제외.

## 2. 착수 체크리스트

- [ ] 사내에서 이 저장소 문서와 코드를 사용할 수 있는 승인된 전달·저장 경로를 확인한다.
- [ ] AGENTS와 요구사항을 읽고, 현재 저장소의 실제 파일·변경 상태를 확인한다.
- [ ] 사내 테스트 폴더와 비식별 데이터, 허용 모델·도구 범위를 준비한다.
- [ ] OpenCode 버전·실행 환경·serve 도움말·health·API 명세를 사내에서 확인한다.
- [ ] 메신저 수신·발신 문서와 비밀값은 사내 승인 위치에만 보관한다.
- [ ] PC 수신 경로·callback·TLS·방화벽·발신 API 접근을 확인한다.
- [ ] 사내 허용 Node.js·패키지 반입·SQLite 드라이버를 확인한다.
- [ ] M0 결과를 기록하고 P01-P03의 최소 골격부터 작업한다.

기존 Windows/WSL 개발 환경을 새로 만들거나 OpenCode를 재설치하는 작업으로 시작하지 않는다. 현재 설치본을 우선 확인한다.

## 3. 메신저 관리 부서 확인표

이 표는 사내에서 작성한다. 외부 저장소에 실제 값이 들어간 표를 커밋하지 않는다.

| 범주 | 물어볼 내용 | 개발에 필요한 이유 |
| --- | --- | --- |
| 수신 | HTTP 등 전달 방식, method·content-type·본문 스키마 | 수신 어댑터 구현 |
| 수신 인증 | 서명 대상·알고리즘·키 관리·timestamp·nonce | 위조·재생 차단 |
| 접수 | ACK 상태·본문·시간 제한, 실패 시 재전송 | 먼저 저장 후 빠른 ACK |
| 이벤트 식별 | event/message ID의 유일성 범위·보존·재시도 시 동일 여부 | 정확한 중복 키 |
| 사용자·대화 | sender·bot·tenant·conversation ID, 1:1 구분 | 본인 허용·원래 대화방 회신 |
| 이벤트 종류 | 봇 echo·수정·삭제·첨부·시스템 메시지 | 루프·잘못된 입력 방지 |
| 발신 | 토큰 발급·갱신, endpoint·body·reply 대상 | 결과 전송 |
| 발신 한도 | 길이 단위·최대값·빈도·429·Retry-After | 분할·backoff |
| 발신 안정성 | idempotency key·전송 조회·server message ID | timeout 후 중복 방지 |
| 네트워크 | PC callback 허용·TLS·DNS·포트·프록시·VM 이전 절차 | 개발·운영 배치 |
| 데이터 | 로그·본문·DB·백업 보관·삭제·반출 기준 | 최소 수집·보안 |

문서 일부가 없다고 사용자에게 인증값을 외부 채팅으로 보내도록 요청하지 않는다. 합성 데이터로 가능한 작업부터 진행한다.

## 4. OpenCode 사내 검증 순서

먼저 기존 설치본의 `--version`, `serve --help`를 확인한다. 해당 도움말과 사내 설정에 맞게 준비된 서버에서 인증·health·명세·전용 세션·요청·SSE를 확인한다. 고정 기본 포트, `--pure` 같은 참고 저장소 인자, 최신 SDK 형식을 무조건 복사하지 않는다.

그 다음 실제 사내 모델을 사용해 합성 파일 읽기, 후속 대화, 실제 질문·일회 승인·거절·중단을 확인한다. 전역 사용자 설정과 기존 세션은 변경하지 않는다. 실제 요청 형식은 [호환성 확인표](opencode-compatibility.md)에 기록한다.

## 5. 첫 개발 에이전트에 전달할 작업 지시

아래를 사내 에이전트의 착수 프롬프트로 사용할 수 있다.

```text
이 저장소의 AGENTS.md, README.md, docs/requirements.md,
docs/implementation-plan.md, docs/handoff.md를 먼저 읽고 기존 변경을 확인하라.

OpenCode는 본인의 사내 PC 설치본 1.18.33을 사용한다.
실제 메신저 API 자료·인증정보·업무 데이터는 승인된 사내 위치에서만 다뤄라.
외부 모델·외부 진단 업로드·메신저 MCP·앱카드·브라우저 연계는 추가하지 마라.

먼저 M0의 로컬 계약·실행환경·보안 확인을 수행하고,
확인된 것/미확인/차단 요인을 구분해 기록하라.
API 자료가 아직 없으면 추정한 실어댑터 대신 합성 어댑터로 진행하라.

P01-P03의 최소 골격을 작은 변경으로 구현하라.
Gateway와 Runner는 같은 PC에서 실행하되 네트워크 계약과 저장 상태를 분리하라.
일반 입력·명령·승인 경계, inbox/outbox, jobId 중복, unknown 무재실행을 지켜라.
이미 준비된 기존 OpenCode serve에 연결하는 방식부터 시작하라.

실행한 검사와 결과를 실제로 기록하고, 합성 통과를 사내 실연동 통과로 표시하지 마라.
실행 스크립트가 생기면 검증한 명령만 README에 추가하라.
매 변경마다 작업 ID·diff·테스트·보안 점검·다음 작업을 보고하라.
```

## 6. 구현 순서에서 흔한 잘못된 출발

agent-browser 전체를 복사해 이름만 바꾸기, Messenger Bridge를 MCP로 먼저 만들기, WebSocket 프록시로 OpenCode 전체 API 노출하기, 최신 버전으로 임의 업그레이드하기, GUI 설치기·메신저 관리 웹앱부터 만들기, 앱카드 업무별 템플릿부터 만들기, 수신 HTTP 응답을 모델 완료까지 붙잡기, 운영 VM에 OpenCode를 설치하기는 이 계획의 출발점이 아니다.

첫 목표는 **합성 입력 왕복 → 실제 PC 파일 기반 답변 → 텍스트 질문·승인·중단을 거친 실제 완료**다.

## 7. 인계 후 진행 기록

작업을 마칠 때 [구현 계획](implementation-plan.md)의 상태와 [테스트 결과 형식](testing.md)을 갱신한다. 실제 구현 명령, 설정 샘플, 지원 OS, 알려진 한계는 검증된 내용만 추가한다. 외부 저장소에는 사내 정책이 허용한 비식별 요약만 남긴다.
