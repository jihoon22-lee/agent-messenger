# agent-messenger

사내 메신저에서 대화하면 **본인의 사내 PC에 있는 OpenCode가 실제 작업을 수행하고 결과를 돌려주는 개인형 챗봇**.

> 상태: **설계·개발 인수인계 문서만 준비된 단계**. 실행 가능한 앱, 설치 명령, 사내 API 연동, OpenCode 1.18.33 실측 결과는 아직 없다. 실제 개발·검증은 보안 정책에 따라 사내에서 진행한다.
>
> 기준일: 2026-10-15. 이 저장소에는 비식별 설계와 합성 예제만 보관한다. 비공개 GitHub 저장소라는 사실은 사내 정보 반출 허가를 의미하지 않는다.

## 만들려는 경험

CLI를 메신저로 복제하는 것이 아니라, 메신저에서 계속 대화하며 본인 PC의 업무를 도와주는 개인 비서를 만든다. 사용자가 말한 “Dot 같은 느낌”은 **지속되는 대화와 실제 작업 능력**에 대한 제품 방향이다. 특정 서비스와의 연동이나 동일한 장기 기억·예약 기능 구현을 뜻하지 않는다.

```text
사용자: 작업 폴더의 보고서 두 개를 비교해줘.
챗봇:   비교할 파일을 확인하고 있습니다.
챗봇:   주요 변경 사항은 세 가지입니다. …
사용자: 두 번째 변경 사항을 더 설명해줘.
챗봇:   두 번째 변경은 …
```

## 확정된 범위

| 항목 | 결정 |
| --- | --- |
| 실제 실행 위치 | OpenCode는 반드시 본인의 사내 PC에서 실행한다. 운영 VM으로 옮기지 않는다. |
| 대상 버전 | 사용자 확인 설치본은 **OpenCode 1.18.33**. API 계약은 사내 설치본에서 검증한다. |
| 수신 서버 | 개발 중에는 사내 PC, 안정화 후에는 수신·발신 Gateway만 운영 VM으로 이전한다. |
| 모델 | 기존 사내 OpenCode에 구성된 사내 LLM을 사용한다. 외부 모델이나 별도 LLM 호출을 추가하지 않는다. |
| 메신저 인터페이스 | 일반 텍스트 우선. 초기에는 앱카드를 만들지 않는다. |
| 메신저용 MCP | 초기 구조에 필요하지 않으며 구현하지 않는다. |
| 세션 | CLI·브라우저 패널과 이어갈 필요가 없다. 메신저 전용 세션으로 대화 맥락을 유지한다. |
| 개발 순서 | agent-messenger 단독 동작을 먼저 검증한다. agent-browser 연결은 이후 확장이다. |
| 개발 장소 | 실제 구현, 사내 API 확인, 통합 테스트는 사내에서 수행한다. |

초기 본인 전용 1:1 사용, 한 번에 한 작업, TypeScript/Node.js/SQLite, Gateway/Runner 분리는 이 문서 묶음의 **권장 구현 기준**이다. 사용자 확정 요구와 조정 가능한 설계 선택은 [요구사항](docs/requirements.md)과 [결정 기록](docs/decisions.md)에서 구분한다.

## 아키텍처

개발 단계에는 두 프로그램을 같은 PC에 두고, 운영 단계에는 Gateway만 옮긴다.

```text
개발
사내 메신저 ↔ Gateway [사내 PC] ↔ Local Runner [사내 PC]
                                      ↕ HTTP API + SSE
                                 OpenCode 1.18.33 [사내 PC]

운영
사내 메신저 ↔ Gateway [운영 VM] ↔ Local Runner [사내 PC]
                                      ↕ localhost HTTP API + SSE
                                 OpenCode 1.18.33 [사내 PC]
```

Runner가 Gateway로 먼저 연결한다. 첫 전송 방식은 인증된 WebSocket을 제안하되 사내 네트워크 정책을 확인한다. OpenCode 포트를 VM이나 메신저 서버에 직접 공개하지 않는다.

- **Gateway:** 수신 인증, 사용자 확인, 수신 저장·중복 감지, 요청 전달, 메신저 발신·재시도.
- **Local Runner:** 전용 세션 연결, 작업 제어, 질문·승인·중단, OpenCode 상태 확인·복구.
- **OpenCode:** 기존 모델·도구·파일 환경을 이용한 실제 실행. Gateway와 Runner는 별도 에이전트 엔진이 아니다.

메신저 연결 정보는 Gateway에, PC 경로와 OpenCode 인증정보는 Runner에 둔다. 세부 구조와 데이터 소유권은 [아키텍처](docs/architecture.md)를 따른다.

## 첫 사용 가능한 버전의 기준

**텍스트 수신 → 실제 PC 작업 → 작업 중 질문·일회 승인 → 최종 답변 전달**이 한 흐름으로 완료되어야 한다. 단순 에코 응답이나 모델 없는 모의 테스트만으로 연동 완료를 선언하지 않는다.

기본 구현에는 전용 세션 유지, 일반 요청 대기열, 제어 메시지 우선 처리, 중복 실행 방지, 긴 답변 분할, 중단, 재시작 복구를 포함한다. PC가 오프라인일 때 접수는 가능하더라도 실제 실행은 불가능하며, 보류 작업을 재연결 즉시 자동 실행하지 않는 것을 초기 정책으로 삼는다.

앱카드, 브라우저 제어, 다중 사용자·단체방, 세션 관리 UI, 복잡한 장기 기억, 예약·선제 알림, ACP/다중 하네스는 초기 범위 밖이다.

## 사내에서 시작하는 순서

1. [AGENTS.md](AGENTS.md)와 [사내 개발 인수인계](docs/handoff.md)를 읽는다.
2. 사내에서 메신저 수신·발신 계약과 OpenCode 1.18.33의 실제 동작을 확인한다.
3. [구현 계획](docs/implementation-plan.md)의 M0부터 진행한다. 실제 API가 준비되지 않은 부분은 합성 어댑터로 격리하되, 실연동 검증과 구분한다.
4. [인수 테스트](docs/testing.md)에서 사내 실측 필수 항목까지 통과한 뒤 개인 파일럿을 시작한다.

현재는 `npm install`, `npm run dev` 등 제품 실행 명령이 **정의되지 않았다**. 구현 단계에서 실제 스크립트를 추가하고 검증한 후 README를 갱신한다.
